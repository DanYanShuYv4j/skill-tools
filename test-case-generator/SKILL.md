# 测试用例生成器

根据 PRD 文档（可搭配交互 Demo）深度分析需求，生成**完整、不截断**的测试用例集。

## 核心铁律

1. **绝对不截断** — 需求有多少测试点就生成多少用例，不省略、不限制数量、不"等等"、不"其余略"
2. **每条业务规则至少正反各一** — 正向验证 + 反向/异常验证
3. **每个边缘情况必须有对应用例** — 分析出的 edge_cases 全部覆盖
4. **每个 UI 元素至少一条 UI 用例** — 按钮、表单、弹窗、下拉等交互组件
5. **模糊需求显式标注假设** — 不明确处生成 P2 用例，预期结果中写"假设：..."
6. **步骤可独立执行** — 不熟悉该产品的测试工程师照着步骤就能测，无需额外上下文

---

## 输入来源

支持三种输入方式：

| 方式 | 用户说 | AI 做什么 |
|-----|--------|---------|
| 单个 PRD | "根据 docs/prd/your-feature.md 生成测试用例" | 读取该 PRD 文件 |
| PRD + Demo | "根据这份 PRD 和 Demo 生成测试用例"（给 PRD 路径 + Demo 目录） | 读取 PRD + 打开 index.html 分析交互 |
| Release 版本 | "根据 V0.9.2 生成测试用例" | 读取 releases/vX.X/README.md → 找到所有关联 PRD 和 Demo → 逐个分析 |

### Release 版本模式详细流程

1. 读取 `releases/vX.X/README.md`
2. 扫描 `modules/*/prd/**/vX.X-*.md` 找到所有该版本 PRD
3. 扫描 `modules/*/demos/**/vX.X-*/` 找到所有该版本 Demo 目录（内层 `{功能中文名}/` 目录中的 index.html）
4. **读取 `releases/vX.X/optimizations.md`（如存在）**，按模块提取优化点清单
5. 按模块逐个读取 PRD 正文，如有 Demo 则同步分析交互；同时将该模块的优化点作为该模块测试用例的一部分
6. 汇总生成一份完整的测试用例文件，保存到 `releases/vX.X/test-cases.md`
7. 更新 `releases/vX.X/README.md`，在末尾追加测试用例链接

## 阶段一：需求分析

在生成测试用例之前，必须对输入进行结构化分析。分析结果以 JSON 格式输出（内部使用，不写入最终文件）。

### 1.1 功能特性提取 (features)

从 PRD 中识别所有功能点，层级最多 5 级：

```json
{
  "features": [
    {
      "id": "F1",
      "path": "用户管理/列表/搜索",
      "description": "按服务类型、空间、关键字筛选服务列表",
      "priority": "P0",
      "source": "PRD §3 R1-R3"
    }
  ]
}
```

提取规则：
- 一级为功能大模块（如"用户管理""订单系统""权限配置"）
- 子级从 PRD 章节标题、需求编号自然提取
- 优先级来自 PRD 中标注的 P0/P1/P2，未标注的根据核心程度推断

### 1.2 用户流程提取 (user_flows)

从 PRD 的用户故事、交互描述和 Demo 中提炼端到端流程：

```json
{
  "user_flows": [
    {
      "id": "UF1",
      "name": "跨空间浏览服务并提交申请",
      "steps": [
        "进入用户列表 → 搜索用户 → 点击详情 → 编辑信息 → 提交 → 确认"
      ],
      "source": "PRD §2 用户故事 + Demo demo.js 流程"
    }
  ]
}
```

### 1.3 业务规则提取 (business_rules)

显式和隐式的规则，每条规则包含正向和反向验证角度：

```json
{
  "business_rules": [
    {
      "id": "BR1",
      "rule": "购物车按空间分组，不同空间的服务不能合并到同一审批单",
      "type": "约束条件",
      "positive_case": "同一空间的服务合并为一个审批单",
      "negative_case": "不同空间的服务被正确拆分",
      "source": "PRD §3 R5"
    }
  ]
}
```

规则类型：约束条件、条件逻辑、访问控制、数据校验、状态转换

### 1.4 边缘情况提取 (edge_cases)

从 PRD 边界场景章节 + Demo 交互推断 + 主动推理：

```json
{
  "edge_cases": [
    {
      "id": "EC1",
      "category": "空状态",
      "description": "购物车为空时提交按钮的展示",
      "source": "Demo demo.js: cart.length === 0"
    }
  ]
}
```

分类：空状态、边界值、并发冲突、超时/断网、权限不足、数据异常、格式错误

### 1.5 UI 元素提取 (ui_elements)

从 Demo HTML 和 PRD 交互描述中提取：

```json
{
  "ui_elements": [
    {
      "id": "UI1",
      "element": "空间视图切换下拉框",
      "type": "下拉框",
      "states": ["默认当前空间", "可切换全部空间"],
      "behavior": "切换后刷新列表和购物车",
      "source": "Demo index.html line 45"
    }
  ]
}
```

### 1.6 歧义标记 (ambiguities)

发现的不明确、矛盾或缺失的需求：

```json
{
  "ambiguities": [
    {
      "id": "AMB1",
      "description": "未说明同一服务能否多次加入购物车",
      "impact": "影响购物车去重逻辑测试",
      "assumption": "假设允许重复加入，数量累加"
    }
  ]
}
```

## 阶段二：测试用例生成

基于阶段一的分析结果，按以下覆盖策略生成完整测试用例。

### 2.1 覆盖策略

| 类型 | 覆盖规则 | 用例类型标记 |
|-----|---------|:---:|
| 正向测试 | 每个 user_flow 至少 1 条 | `功能` |
| 异常测试 | 每条 business_rule 至少 1 条反向用例 | `异常` |
| 边界测试 | 涉及数值/长度/容量的规则 → 最小值、最大值、空值、超限 | `边界` |
| UI/UX 测试 | 每个 ui_element 至少 1 条 | `UI` |
| 边缘情况测试 | edge_cases 全覆盖 | `功能`/`异常`/`边界`（视场景） |
| 集成测试 | 跨模块流程 | `集成` |
| 优化点测试 | 从 optimizations.md 提取，按类型简化为 1-2 条 | `优化` |

### 2.1.1 优化点 → 测试用例转换规则

当 Release 版本中存在 `optimizations.md` 时，按以下规则为每条优化点生成测试用例：

| 优化类型 | 生成策略 | 用例数 |
|---------|---------|:---:|
| `UI` | 生成 1 条 UI 用例，验证元素位置/样式/文案是否符合优化描述 | 1 |
| `交互` | 生成 1 条功能用例，验证交互行为是否符合优化描述 | 1 |
| `规则` | 生成 2 条（1 条正向验证规则生效 + 1 条反向/边界验证） | 1-2 |

**优化点用例的字段约定**：
- **测试用例ID**：与 PRD 用例共用同一模块前缀，顺延编号（如数据质量模块 PRD 用例到 `TC-数据质量-014`，优化点从 `TC-数据质量-015` 开始）
- **模块**：`优化清单/{模块名}`
- **测试场景**：`验证{优化点描述}`
- **前置条件**：从优化描述中推断（如"用户已登录、进入 XX 页面"）
- **优先级**：沿用优化清单中的 P 值
- **类型**：统一标为 `优化`

### 2.2 优先级判定

结合 PRD 需求优先级和测试重要性：

| PRD 优先级 | 正向用例 | 异常/边界用例 |
|:---:|:---:|:---:|
| P0 | P0 | P1 |
| P1 | P1 | P2 |
| P2 | P2 | P2-P3 |
| 未标注 | 核心流程 P0，其他 P1-P2 | P2 |

### 2.3 输出格式

**仅输出测试用例表格，无需需求分析摘要、覆盖统计等章节。**

以 Excel 文件（.xlsx）输出，包含以下列：

| 测试用例ID | 模块 | 测试场景 | 前置条件 | 测试步骤 | 预期结果 | 优先级 | 类型 |
|-----------|------|---------|---------|---------|---------|:---:|:---:|

**各列规范：**

**测试用例ID** — `TC-{一级模块}-{序号}`，序号为三位数字（001, 002...），同一一级模块内连续编号。
- 示例：`TC-用户管理-001`、`TC-用户管理-002`

**模块** — 从 features 提取的层级路径，用 `/` 分隔，如 `用户管理/列表/搜索`。

**测试场景** — 一句话描述正在验证什么，格式：`验证 + 什么条件 + 产生什么行为/结果`。
- ✅ 好："验证购物车为空时点击提交按钮，按钮置灰不可点击"
- ❌ 差："测试购物车"

**前置条件** — 执行测试需要的数据、状态、权限。多条用分号分隔。

**测试步骤** — 编号的祈使句，足够具体可独立执行：
```
1. 以空间管理员身份登录系统
2. 进入用户管理页面
3. 在搜索框输入"测试服务"
4. 点击搜索按钮
```

**预期结果** — 精确、可观察的结果。模糊需求显式标注假设：
- "搜索结果列表仅显示名称包含'测试服务'的服务项"
- "假设最多重试 3 次：第 4 次重试时提示'操作频繁，请稍后再试'"

**优先级** — P0（核心流程阻断）、P1（主要功能）、P2（一般功能/异常/边界）、P3（细节/优化）。

**类型** — `功能`、`UI`、`边界`、`异常`、`集成`、`优化`

### 2.4 去重规则

生成后检查并合并以下重叠情况：
- 步骤完全相同的用例 → 合并为一条，取更高优先级
- 正向流程覆盖了 UI 元素验证的 → 不重复生成 UI 用例，在正向用例中补充 UI 验证步骤

## 阶段三：输出和保存

### 3.1 保存位置

| 输入方式 | 输出路径 |
|-----|------|
| 单个 PRD | 询问用户保存位置，默认建议 `releases/vX.X/test-cases-{功能名}.xlsx` |
| Release 版本 | `releases/vX.X/test-cases.xlsx`（自动确定） |

### 3.2 文件格式

Excel 文件（.xlsx），仅包含一个 Sheet「测试用例」。列：

测试用例ID | 模块 | 测试场景 | 前置条件 | 测试步骤 | 预期结果 | 优先级 | 类型

- 表头行加粗、冻结首行
- 列宽自适应内容
- 步骤列中多条步骤用换行符分隔

### 3.3 更新 release README（Release 版本模式）

如果是为整个 release 生成测试用例，在 `releases/vX.X/README.md` 末尾追加：

```markdown
## 🧪 测试用例

完整测试用例：[test-cases.xlsx](test-cases.xlsx)（N 条用例）
```

## 示例

### 用户说

> 根据 docs/prd/your-feature.md 和 demos/your-feature/ 生成测试用例

### AI 执行

1. 读取 PRD → 提取功能（用户管理/列表/详情/编辑 等）
2. 打开 Demo index.html → 分析 demo.js 交互流程 → 提取 UI 元素（搜索框、筛选下拉、购物车图标、提交按钮、空间切换...）
3. 识别业务规则（跨空间分组、审批人选择、购物车去重...）
4. 识别边缘情况（空购物车、无匹配服务、网络断开...）
5. 识别歧义（同服务重复加入、单次申请数量上限...）
6. 生成完整测试用例（不截断）
7. 询问保存位置，输出文件

## 项目约定

- 仓库根目录：`/path/to/your/project`
- PRD 路径：`modules/<module>/prd/<author>/v{版本号}-{slug}.md`
- Demo 路径：`modules/<module>/demos/<author>/v{版本号}-{模块}/{功能中文名}/`
- Release 路径：`releases/vX.X/`
- 测试用例文件名：`test-cases.xlsx` 或 `test-cases-{功能名}.xlsx`
