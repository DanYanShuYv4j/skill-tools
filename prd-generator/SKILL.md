# PRD 对话式生成器

以 5 步对话引导用户完成一份高质量 PRD。核心原则：**开发拿到后能直接开始干活**。

## 核心铁律

1. **永远不在用户确认前生成文件**——用户明确说"生成"才写 `.md`
2. **逐节推进**——每次只问一个步骤
3. **允许跳过**——不适用就标记"待补充"，不阻塞流程
4. **允许回退**——用户说"回到上一步"或"修改第 X 步"，立即跳转
5. **主动提示**——每步完成后给出 2-4 个用户可能遗漏的思考方向
6. **发现矛盾先澄清**——如果用户前后表述不一致（如 P0 需求 A 和 P0 需求 B 技术上冲突），先指出矛盾让用户确认，不要自作主张取舍
7. **变更记录强制**——写入文件后必须执行步骤 8（变更记录），不可跳过。修改已有 PRD 时自动扫描差异并让用户确认

## 三种工作模式

### 模式 A：新建文档

用户说"帮我写一份 PRD"→ 先确认模块和版本（步骤 0），再从步骤 1 开始，走完 7 步，生成完整文档。

**文件名规则**：`v{版本号}-{模块}.md`。一人一版本一模块一个 PRD，同一版本同一模块下的功能合并到一个文件。

### 模式 B：插入已有文档

用户提供现有 PRD 文件路径，说"帮我补充 XX 章节"→ 先读取文档，理解已有结构和内容风格，然后只走相关步骤。结果**插入到文档的指定位置**，不覆盖已有内容。

### 模式 C：轻量改动

用户描述一个小改动（加按钮、改交互、调文案），**不是完整功能**。判断标准：改动单点、无需背景铺垫、一句话能说清楚。

触发：用户说"加个清空按钮""把这里的交互改一下""这个需求就一个小点"。

**轻量模式规则**：
- 只走步骤 4（功能需求），其他步骤跳过
- 不追问背景、用户故事、不做范围、边界场景
- 快速确认需求 → Given/When/Then → 生成或插入

如果用户说的改动实际上影响面很大（涉及多个模块、数据模型变更），提醒"这可能需要完整 PRD"，让用户选择是否切换到模式 A。

### 模式 D：优化清单录入

用户描述的单点改动**不涉及新页面/新流程**，且改动量极小（一句话能说清），适合放入版本优化清单而非独立 PRD。

触发判断：当用户描述的内容符合以下特征时，主动问「这个算优化清单还是单独写 PRD？」：
- 不涉及新页面/新流程
- 不改变现有交互逻辑，只是补充/修正
- 文案、样式、校验规则等单点调整

**优化清单规则**（极简 2 步）：

**步骤 1：确认模块**
> "这是哪个模块的优化？"（列出你项目里的模块，让用户选）

**步骤 2：收集信息**
> "一句话描述一下优化内容，以及优先级（P0-P3）："

确认：
- 优化点：一句话描述
- 类型：`UI`（视觉/文案调整）/ `交互`（行为补充/修正）/ `规则`（校验/逻辑调整）
- 优先级：P0 / P1 / P2 / P3
- 备注（可选）：关联 PRD、关联需求编号等

不追问背景、用户故事、不做范围、边界场景、Given/When/Then。

## 对话流程

### 步骤 0：确认模块与版本（模式 A 必须）

在进入需求细节之前，先确认两件事：

**第一问：归属哪个模块？**
> "这个 PRD 归属哪个模块？"（列出你项目里的模块名让用户选，或让用户直接说）

**第二问：归属哪个版本？**
> "归入哪个版本？"（如 v1.0.0）

确认后告知文件名：
> "将生成 `v1.0.0-{模块}.md`，对吗？"

**文件名 = `v{版本号}-{模块}.md`**。

如果同版本同模块已有 PRD 文件存在，提示用户"已有同模块 PRD，将合并追加到现有文件"。

### 步骤 1：背景与问题

**问**：为什么要做这个功能？当前用户怎么做的？哪里痛？

**输出**（一段话，不超过 200 字）：

```
## 1. 背景

运营团队每周五需要手动从 3 个平台导出数据拼成周报，每次耗时约 1.5 小时，数据口径经常不一致。
```

**主动提示**：
- 这个问题的频率有多高？（每天？每周？）
- 有没有具体的数字可以量化？（耗时、出错率）
- 不做的后果是什么？

### 步骤 2：用户故事

**问**：谁要干什么？达到什么目的？3-5 个核心故事。

**格式**：`As {角色}, I want to {做什么}, so that {目的}`

**常见错误，发现时立刻提醒**：
- 太模糊："作为用户，我希望产品更快"→ 追问：哪一步快？
- 太方案化："作为用户，我希望有一个下拉菜单"→ 追问：你需要什么功能？
- 一样大："作为用户，我希望管理项目"→ 追问：管理包含哪些？先做哪个？

**输出**：

```
## 2. 用户故事

- As 运营, I want to 一键导出周报数据, so that 不用手动拼表
- As 负责人, I want to 看到数据口径来源, so that 能复核结果
```

**主动提示**：
- 首次使用怎么做？（onboarding）
- 失败后怎么办？（重试/编辑/删除）
- 中途退出再进来怎么办？

### 步骤 3：角色与权限

**问**：这个功能涉及哪些角色？每个角色的权限边界是什么？

从步骤 2 的用户故事中提取角色，**列给用户确认**，不自行补充用户故事之外的角色：

> "从用户故事看，涉及的角色有：{角色1}、{角色2}…，对吗？需要补充吗？
> 各自的权限边界是什么？（谁能操作/查看，谁不能）"

**输出**：

```
## 3. 角色与权限

| 角色 | 定位 | 权限要点 |
|-----|------|---------|
| {角色1} | …… | …… |
```

**主动提示**：
- 是否有角色做不了某些操作？（权限边界）
- 是否有管理员/普通用户之分？
- 权限是全局还是按空间/租户隔离？

如果用户对权限细节不确定，标注「待确认」，**不自行编造角色或 Y/N 权限矩阵**。

### 步骤 4：功能需求

**先问 P0，再问 P1，最后 P2**。

**判断 P0 vs P1**："如果砍掉这个，核心场景还能跑吗？"→ 能就是 P1，不能就是 P0。

每条需求包含：
- 交互逻辑：用户看到什么、怎么操作
- 验收条件：Given/When/Then，至少 3 条（含 1 条异常路径）

**Given/When/Then 写作指南**：
- Given 写前置条件（"用户已登录，文件夹中已有 5 份 PDF"）
- When 写具体动作（"将新 PDF 拖入 drop zone"）
- Then 写可观察结果（"文件出现在列表中，状态显示'索引中'"）
- 覆盖 1 条异常路径（如"拖入不支持的格式 → 提示'暂不支持此格式'"）
- 避免模糊词："快"、"好用"、"合理"

**每轮提示异常清单**（3-5 条）：

```
这条需求可能的异常情况：

A. 加载中 → [ ] skeleton [ ] spinner [ ] 置灰
B. 加载失败 → [ ] 错误+重试 [ ] toast [ ] 静默
C. 数据为空 → [ ] 空状态引导 [ ] 正常显示 [ ] 隐藏
D. 网络断开 → [ ] 队列兜底 [ ] 直接失败 [ ] 自动重连
E. 权限不足 → [ ] 置灰入口 [ ] 提示无权限 [ ] 隐藏入口
```

**输出**（表格）：

```
## 4. 功能需求

### P0 需求

| # | 需求 | 交互 | 验收 |
|----|------|------|------|
| R1 | 文件拖入索引 | 拖入文件夹→显示进度→完成后可用 | Given...When...Then... |
```

### 步骤 5：不做范围

**问**：明确不做什么？防止范围蔓延。

**主动提示**：列出 3-5 个容易被误认为在范围内的项让用户判断。

**输出**（表格）：

```
## 5. 不做范围

| # | 不在范围内 | 原因 |
|---|-----------|------|
| N1 | 移动端适配 | 桌面端专属 |
```

### 步骤 6：边界场景

**分 4 类，每类问 2-3 条**：

- 数据异常：空数据、格式错、超大文件
- 状态冲突：关联对象被删除、引用失效
- 并发：快速重复点击、同时修改
- 超时/断网：接口超时、网络断开

**输出**（表格）：

```
## 6. 边界场景

| # | 场景 | 预期行为 |
|---|------|---------|
| B1 | 拖入损坏的文件 | 提示"文件损坏，无法解析" |
```

### 步骤 7：非功能性需求

**问**：这个功能有哪些非功能性要求？逐类确认，只记录用户明确提出的：

- **性能**：响应时间、并发量（p50/p95、测量条件）
- **安全**：权限控制、数据加密、审计
- **可靠性**：异常告警、回滚、容错
- **容量**：数据量级、存储
- **可维护性**：日志、监控、扩展性

**输出**：

```
## 7. 非功能性需求

| 类别 | 需求 | 指标/说明 |
|-----|------|----------|
| 性能 | …… | …… |
```

**规则**：只写用户明确提出的非功能需求；用户没提的类别不编造，写「无」。用户不确定的指标标注「待确认」。

---

## 最终汇总与生成

所有步骤走完后，汇总预览（不写文件）。

确认：
- [ ] 标题确认
- [ ] 输出路径
- [ ] 步骤 3 角色与权限是否已与用户确认（只列用户确认的角色）
- [ ] 步骤 7 非功能性需求是否已与用户确认（无依据类别写「无」）
- [ ] 所有"待补充"章节是否可接受

**用户确认后写入文件。**

---

## 步骤 8：变更记录（强制，不可跳过）

写入文件后**必须**处理变更记录。这是强制步骤，不可跳过。

### 模式 A：新建 PRD

自动在文件末尾追加初始变更记录（版本号暂用「待定」）：

```markdown
## 变更记录

| 版本 | 日期 | 作者 | 变更内容 |
|-----|------|------|---------|
| 待定 | 日期 | {作者} | 初始版本：{PRD 标题} |
```

### 模式 B / C：修改已有 PRD

1. **扫描变更**：对比修改前后的内容，识别差异（新增章节、修改需求、删除内容、调整优先级等）

2. **汇总给用户确认**：

```
检测到以下变更，请确认：

- 新增：R11-R15 数据表权限申请章节
- 修改：R8 批量勾选从单选改为统一提交
- 删除：R5 审批超时策略（移至不做范围）

这些变更记录是否正确？有需要补充或修改的吗？
```

3. **用户确认后**，追加/更新 PRD 末尾的「变更记录」表：

```markdown
| v1.1 | 日期 | {作者} | 新增数据表权限申请(R11-R15)；批量勾选改为统一提交；审批超时策略移至不做范围 |
```

4. **如果已有同版本记录**（用户在同一天多次修改同一版本），更新该条记录而非新增行

### 变更摘要提取规则

从实际内容差异中提取，不用用户自己写：

| 变更类型 | 前缀 | 示例 |
|---------|------|------|
| 新增章节/需求 | 新增 | 新增R11-R15数据表权限申请 |
| 修改已有内容 | 变更/修改 | 批量勾选改为统一提交 |
| 删除内容 | 删除/移除 | 删除审批超时策略 |
| 调整优先级 | 调整 | R5从P0降为P1 |

### 变更记录位置

- PRD 文件末尾追加「## 变更记录」章节
- 如果文件已有变更记录，追加新行（最新版本在最前面）

## 技巧

### 给选项而非给答案

```
文件加载过程中 UI 应该怎么展示？
A. 骨架屏占位
B. Loading spinner
C. 暂不展示该区域
```

### 追问量化

用户说"性能要好"，追问：多快算好？p50 还是 p95？测量条件？

### 识别模糊词

"支持多种..."→ 具体哪几种？"必要时..."→ 触发条件？"等等"→ 还有哪些？
